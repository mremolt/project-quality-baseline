# Quality Baseline: Architecture at a Glance

The current architecture, technologies and decisions of the quality baseline, for people who want the picture without reading every rule. The rules themselves are in [docs/baseline/](docs/baseline/README.md); where this page and the rule docs differ, the rule docs are right.

This page describes the current state only and changes together with the baseline (DOC-ARC-09).

## What it is

The quality baseline is our shared answer to "how do we build web software here?". It is a set of documents (an arc42 reference architecture), agent skills and templates. A product repository does not depend on it at build time: a sync script copies it in, and the team commits the result.

Each product then documents only what is specific to it: its own arc42 chapters in `docs/architecture/` and its decisions as ADRs in `docs/adr/`.

Rules have stable IDs (for example `ARCH-UC-01`); a deprecated or duplicate rule is removed, and its ID is retired, never reused. **MUST** rules can only be deviated from with an ADR; **SHOULD** rules are defaults that a team may leave with a stated reason. A rule without a keyword is a MUST unless it says *prefer*, *default* or *consider*. Coding agents (Claude Code, Codex, Copilot) read the same rules through `AGENTS.md` and the skills, and the docs win over any skill.

## Quality goals, in priority order

1. **Changeability**: business logic does not depend on frameworks or infrastructure.
2. **Testability and confidence to ship**: a green build means "releasable".
3. **Accessibility**: WCAG 2.2 AA, proven by tests.
4. **Security**: secure defaults, designed in, checked in the pipeline.
5. **Consistency**: the same structure, names and commands in every repository.
6. **Operability**: the application can be configured, deployed, observed and shut down safely.

## Architecture

Backends and frontends both use a **hexagonal architecture** (ports and adapters). Code is organised in four rings, and dependencies only point inward. Domain, ports and application together are called the *core*.

| Ring | Contains | May depend on |
|---|---|---|
| Domain | Entities, value objects, business rules, business exceptions and domain events | nothing |
| Ports | Interfaces: incoming (one per use case) and outgoing (what the core needs) | domain |
| Application | One service per use case, orchestrating the domain through ports | domain, ports, a short allow-list (transactions, logging, observation) |
| Adapters | REST controllers, message listeners, UI, database, HTTP clients, schedulers | everything inward; never another adapter |

What follows from this:

- **One class per use case**, reachable only through its incoming port. Queries are separate from commands. The adapter authenticates and builds the caller; the use case authorizes.
- **Bounded contexts meet only at incoming ports.** A context calls another through its own outgoing port; a shared kernel needs an ADR. In the frontend, a feature uses another only through its published provider, and feature routes load lazily.
- **Errors are modelled the same way everywhere.** Business errors are exceptions in six categories (validation, access denied, business rule, not found, conflict, technical), with one table that says how HTTP, message consumers and the UI handle each. Results are only for expected alternative outcomes.
- **Domain events** are handed to an outgoing port and published through the transactional outbox; use cases never call each other.
- **Models are mapped at the boundaries.** The database entity is never the domain model; API types never reach the core.
- **The frontend follows the same rings.** Components and the view-state store (NgRx Signal Store in Angular, Redux Toolkit slices in React) are the UI adapter and hold view state only; server data in React lives in TanStack Query, whose queries and command mutations call use cases, injected through one context per feature published from its `<feature>.api.tsx`; use cases hold the logic; generated HTTP clients are outgoing adapters that map problem codes to domain errors and report the technical errors they create.
- **A Next.js app keeps the rings on the server too.** Server components, server actions and route handlers are incoming adapters that call use cases from a request-scoped composition; `src/app/` only routes. The app is its own image and the BFF for its browser users; server actions are public endpoints.
- **Boundaries are enforced by tests from day one**, not by convention. ArchUnit finds adapters by package and stereotype (web, persistence, messaging, scheduling, metrics, HTTP client, mail, file), checks cycles, the application allow-list and that every class has a valid home. dependency-cruiser does the same for TypeScript frontends and Node backends, also sees type-only imports and covers the shared `platform` folder.
- **A NestJS backend keeps the same rings as Spring.** Each bounded context's Nest module is its composition root; use cases are plain classes without decorators, created by factories and injected by token; the transaction boundary is an outgoing port the use case calls.
- **Shortcuts are allowed, but never silently.** Each one is proposed and recorded as an ADR; following a documented default needs none.

## Technology

| Area | Choice |
|---|---|
| Backend | Java 25, Maven wrapper, Spring Boot 4.1 (Spring MVC on virtual threads) by default; NestJS 12 on Fastify (Node.js 26 LTS, TypeScript 6, ES modules) as the documented alternative, chosen per product |
| Data | PostgreSQL by default with forward-only migrations. Spring: Flyway, Spring Data JPA for aggregates and `JdbcClient` for reads, bulk work and tables without aggregate invariants. NestJS: Kysely (typed SQL, no ORM) and the Kysely migrator. A rule across rows (no overlap, "at least one") is held by a database constraint or lock and proven by a parallel test |
| Messaging | Kafka by default (rules phrased as broker capabilities), JSON payloads with a typed envelope, transactional outbox with a relay, AsyncAPI contract. NestJS uses `@platformatic/kafka` (pure JavaScript) in own adapters |
| Frontend | TypeScript (strict). Angular current major (standalone, signals, zoneless), Angular Material (Material Design 3) and NgRx Signal Store by default. Documented alternatives, chosen per product: React SPA (React 19 with the React Compiler, Vite 8, TanStack Router with code-based routes, Redux Toolkit for view state, TanStack Query, MUI 9, React Hook Form) and Next.js 16 (App Router on the same React layer). React and Next.js projects never load Angular docs or skills, and the other way round |
| API | REST with OpenAPI, code-first (springdoc, or `@nestjs/swagger` from zod schemas); the spec is committed; clients are generated (Orval), never hand-written; shared wire-format conventions (decimals as strings, dates, enums, paging, sorting, filtering, ETags, deprecation headers); errors as RFC 9457 problem details with a stable `code` |
| Authentication | External identity provider (OIDC), Keycloak by default when the product has none; users are provisioned through an outgoing port to its admin API; backend validates JWTs as a resource server once a non-browser client exists (Spring Security, or `jose` in a NestJS guard); browsers log in through a backend-for-frontend, a confidential OIDC client with PKCE, with a session cookie, fixed session lifetimes and logout at the identity provider. A Spring BFF keeps its sessions in Spring Session JDBC on the product's PostgreSQL, so they survive restarts and are shared between instances. The BFF is a Spring or a NestJS service, or the Next.js app itself; Node BFFs share framework-neutral rules (`openid-client`, server-side session store in Redis or Postgres, `__Host-` cookie, XSRF header, nonce CSP) |
| Observability | Health probes on the serving port, OpenTelemetry metrics and traces over OTLP (Micrometer in Spring, the OpenTelemetry Node SDK in NestJS), structured JSON logs on stdout (Logback or pino), frontend error reporting; a Next.js server uses the OpenTelemetry Node SDK and pino like NestJS and takes the browser's error reports in its own `/client-errors` route handler |
| Backend tests | Spring: JUnit, AssertJ, Mockito, Testcontainers, ArchUnit. NestJS: Vitest (with SWC), vitest-mock-extended, Testcontainers, dependency-cruiser |
| Frontend tests | Vitest, Testing Library, Playwright with axe; E2E runs against the production build behind a strict nonce CSP and fails on CSP or Trusted Types violations. A Next.js app stubs the backend and the IdP with MSW inside its own server in test mode, guarded so the stubs never start in a deployed environment |
| Code quality | Java: Spotless, Error Prone with NullAway, SpotBugs with FindSecBugs. TypeScript (frontend and Node): ESLint (type-checked, SonarJS, `@vitest/eslint-plugin` for specs, `eslint-plugin-playwright` for E2E; Node adds security and ReDoS rules; React adds react-hooks with the React Compiler checks, `@eslint-react`, `jsx-a11y-x`, TanStack Query and, for Next.js, `@next/eslint-plugin-next`), Prettier, dependency-cruiser, knip (unused dependencies, exports and files) |
| Internationalisation (optional per product) | Transloco with an eval-free ICU transpiler on `intl-messageformat` (Angular), `use-intl` (React SPA) or `next-intl` (Next.js) in the frontend, message bundles in the backend, Weblate for translators |
| Local development | Docker Compose for the services a backend needs, images pinned |
| Container images | OCI image, non-root, minimal pinned base, SBOM. Buildpacks by default; a Dockerfile or Jib when the customer platform dictates it. NestJS services use a multi-stage Dockerfile on distroless, because the Paketo Node buildpack cannot run Node 26 yet. The BFF image also carries the frontend bundle (Angular, React SPA) and refuses to start without it; a Next.js app is its own distroless image built from its standalone output with a Dockerfile, read-only and non-root |

CI/CD, registry, hosting, the orchestrator and the scanners are **not** fixed by the baseline. They depend on the customer's infrastructure. The baseline states what the pipeline and the application must do as capabilities, names replaceable reference tools, and each product records its concrete tools in a delivery platform mapping in its chapter 7.

## Key decisions

| Topic | Decision |
|---|---|
| Stack choice | Spring Boot backend and Angular frontend by default. NestJS, the React SPA and Next.js are documented alternatives a product picks in its chapter 4 without an ADR; Next.js only for a stated reason the SPA cannot meet (server-rendered public pages, a measured first-paint budget, streaming). The product declares its stacks in `.baseline.json`. |
| Repository | One repository per product, with `backend/` and `frontend/` folders. Separate repositories need a reason from the decision guide and an ADR. |
| Testing | Each architecture element has its test type, style and test doubles, defined in one table: unit tests for domain and use cases, integration tests for adapters against the real technology, system tests for main paths. Frontend system tests stub our backend from the contract and run on every pull request; a few full-stack tests stub only third parties. Written test-first, with deterministic test data (builders, fixed clocks and ids; fakers only seeded and for volume). |
| Coverage | Reported, not gated; the TypeScript templates ship the report (`test:coverage`). The measure is confidence to ship, and every production bug gets a test that would have caught it. Mutation testing on the core is optional and reported. |
| API contracts | A breaking API change fails CI before merge. |
| Data loading | Every data-loading change is checked for N+1 requests; the developer decides the strategy. Collections are paged or have an enforced upper bound. |
| Accessibility | WCAG 2.2 AA is mandatory, with a chosen set of AAA criteria as the default. Six test layers, from lint to a manual release checklist with a desktop screen reader; the E2E suite also scans dark, high-contrast and forced-colors themes. Each product keeps a journey and screen inventory and records whether the European Accessibility Act applies. Mobile assistive technology is decided per product. Accessibility checks are never switched off to pass a build. |
| End-to-end tests | One default cell (browser, viewport, theme, locale); the matrix grows one dimension at a time. Pull-request E2E has a time budget; retries only in CI (one retry, workers capped), and a flaky test is fixed or quarantined with a ticket within a week. Each scenario creates its own data and arranges time-dependent state through the API instead of waiting. |
| Security | OWASP ASVS 5.0: level 2 is the target, level 1 the minimum to release. Each product keeps a threat model and records whether the EU Cyber Resilience Act applies. Dependency, secret and code scans run on every pull request; images are scanned before release and again on a schedule; provenance is signed and verified before deployment; an external penetration test precedes go-live. Fix times: critical 7 days, high 30, medium 90, counted from detection. Shared rules for cryptography and the audit trail. |
| Data protection | Each product keeps a personal-data inventory and a deletion concept, updated in the same change that adds personal data; dead letters, inbox and idempotency stores are in scope. The controller decides on breach notification, the DPO advises; as a processor we inform the customer. Production personal data never enters other environments. |
| Delivery | Trunk-based development with squash merges and Conventional Commits. One image per commit, identified by commit SHA and digest, promoted unchanged through all environments; the release version is attached without a rebuild and injected at deploy time. Production needs a recorded approval. Customers who deploy themselves get a handover package. |
| Deployments | Rolling, with at least two instances of every server-side deployable (backends, BFFs, Next.js apps). Every version works alongside the previous one (API, events, database schema, frontend chunks), so rollouts and rollbacks are safe. Migrations run at start-up by default, or as a pre-deploy job with the same image. The schema is never rolled back; faulty releases are fixed forward by default, and rollback and restore are rehearsed. A container runtime contract covers privileges, read-only filesystem, resources, start-up and termination. |
| Resilience | Every outbound call has explicit timeouts, fitted into one timeout ladder per product (gateway > request > transaction > statement). Only idempotent operations are retried, with a total time limit. Concurrency towards each dependency is bounded; at the limit a caller fails fast or waits a bounded time, never unbounded. No remote call inside a database transaction. Every message consumer is idempotent. |
| Configuration | Typed and validated at start-up; every component keeps a machine-readable list of its keys. Secrets come from a secret manager, never from git, and are held in a self-masking type. The frontend loads its environment settings at runtime, so one build serves all environments. Demo data is loaded through the use cases under a `demo` profile that deployed configurations never set. |
| File exports | Machine-readable exports have one fixed format chosen by their consumer; human-readable exports follow the recipient's language. Spreadsheet exports neutralise formulas, XML and PDF are built with writers, never strings, server-side rendering has no network access, and generated PDFs are validated for PDF/UA. File-rendering features run once against the real image. |
| Builds | Reproducible on every stack (fixed timestamps, `npm ci`, pinned toolchains and images), with an SBOM for backend and frontend. Dependency updates come from update automation covering all ecosystems. |

## How the rules are kept

- **In the build**: architecture tests, compiler checks, linters, accessibility tests, contract checks and security scans fail the build. None of them may be weakened to get a build green (SEC-REV-02). A component's `verify` command is its local gate and reports every failing check in one run; `check` is the fast inner loop; one pipeline jobs table says what CI runs. On a red gate, agents run the autofix commands first and fix only the rest by hand.
- **In review**: the pull request template carries the security, N+1 and delivery checklists; reviewers cite rule IDs.
- **By agents**: entry skills (`baseline-spring`, `baseline-nestjs`, `baseline-angular`, `baseline-react`, `baseline-nextjs`, `baseline-security`, `baseline-i18n`, `baseline-tdd`) route agents to the right rules before they write code; the Spring, NestJS, React and Next.js entry skills also carry the templates for a new component, and the Angular and Spring skills ship generators for a feature and a use case (the ~10 and ~8 files that otherwise drift from the rings; the Spring one optionally adds the controller and its slice test); the Spring skill also ships shared test fakes and a Keycloak realm template. Each product declares its stacks in `.baseline.json`, where the sync also records the baseline commit it synced, so the next sync can list the project-owned templates that changed since then; the sync installs only those stacks' skills, agent instructions and Claude Code reminder hooks (each entry stack owns one that reminds the agent to load its entry skill before the first edit in a component of that stack), and each stack's docs are self-contained, so agents never load another stack's rules. Because one stack chain alone runs to 50,000–100,000 words, agents never read it whole: they start from a generated rule index (`docs/baseline/rule-index/`, every rule ID with its one-sentence headline, about a tenth of the text, one file for the shared rules and one per stack) and open full docs only for the topics their task touches. Agent checklists and sources live outside the rule docs (`docs/baseline/checklists/<scope>.md`, `docs/baseline/sources.md`), so a doc opened for its rules carries only rules; agents read the checklist sections of the docs they used once, before finishing. A lint (`docs:lint`) checks these rules, and a baseline-only agent (`baseline-doc-compactor`) runs it periodically, fixes its findings and compacts the docs changed since its last run without dropping information; changes that would alter a rule come back as proposals. A script generates the index from the docs, a check fails when it is stale, and the sync refuses to ship a stale one; for that to work, every rule starts with a bold headline that states the rule on its own. A kickoff prompt (`prompts/project-kickoff.md`, not synced) starts an unattended implementation from a product's planning documents with the baseline as its technical specification, and has the agent log where the baseline fell short. A review skill (`baseline-codebase-review`, kept in the baseline repository and never synced) reviews an existing codebase twice, once on expertise alone and once against the baseline; what only the first review found becomes proposals for the baseline, and the codebase gets the updated baseline and a refactoring report for its own agent.
- **By decision record**: any deviation from a MUST is an ADR in the product repository.

## What the baseline does not cover

- Product requirements and the infrastructure the application runs on (clusters, networks, backups, monitoring stack, on-call). Each product documents these.
- Known open points, listed in [chapter 11](docs/baseline/11-risks-and-technical-debt/README.md): performance and load testing rules, parts of the frontend error and UX policy, a REST removal timeline for old majors, a single Definition of Done, a business change log with old and new values (left to product ADRs), multi-tenancy beyond tenant isolation, and legal and DPO confirmation of the CRA, EAA and breach-notification rules.
- Most operability, security hardening and i18n rules were written from documentation and have not yet been exercised in a product. Chapter 11 lists the concrete checks to run before first use; the first product that adopts them confirms or corrects them.
