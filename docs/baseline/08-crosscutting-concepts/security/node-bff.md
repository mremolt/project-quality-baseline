# Node.js Backend-for-Frontend

Rules for a backend-for-frontend (BFF) that runs on Node.js, whatever the framework. A NestJS backend (NEST-D7) and a Next.js frontend (NEXT-D*) can both be the BFF; their stack files add only the framework wiring (NestJS: NEST-SEC-44..52 in [nestjs-hardening.md](nestjs-hardening.md); Next.js: [nextjs.md](nextjs.md)). The Spring BFF follows SPRING-SEC-08/09, 24/25 and 32/33 instead.

Why a BFF at all: SPRING-SEC-08 and its NestJS twin NEST-SEC-12. The browser holds a session cookie, never a token.

These rules are written from documentation and scratch tests of the libraries; no product has run them yet ([chapter 11](../../11-risks-and-technical-debt/README.md#verify-before-first-use)).

## Role

- **NODE-BFF-01: The BFF logs users in, holds their tokens and serves the frontend; it has no business logic.** It offers login, login callback, `POST /logout`, the back-channel logout endpoint, the CSP report endpoint, the frontend and its runtime configuration (CFG-11). Calls to the API go to the resource server with the user's access token (token relay) through an outgoing adapter with explicit timeouts (RES-TMO-01). A BFF that is also the resource server verifies the session's access token with the same function its API guard uses (one validation path). A product records which component is the BFF in an ADR (NEST-SEC-13, NEXT-D*).

## Login and session

- **NODE-BFF-02: OIDC login uses `openid-client` 6 with authorization code and PKCE.** `discovery(issuerUrl, clientId, metadata, clientAuth, { timeout })` once per process, at start-up or, where the framework evaluates modules at build time, at the first login with a failed discovery not cached (NEXT-SEC-01) (the timeout then applies to all its requests); client authentication `PrivateKeyJwt` where the IdP supports it, otherwise `ClientSecretBasic`/`ClientSecretPost`. Login: `randomPKCECodeVerifier()`, `calculatePKCECodeChallenge()` (S256), `randomState()` and `randomNonce()` stored server-side as pre-login state together with the post-login target, then `buildAuthorizationUrl(config, {...})`. Starting a login never replaces or ends a live session: the pre-login state lives either in the current server-side session, or in a separate short-lived pre-login record under its own cookie (Next.js: `__Host-login`, NEXT-SEC-01), and the session cookie is (re)issued only by a successful callback. The callback consumes the pre-login state (one use). Callback: `authorizationCodeGrant(config, currentUrl, { pkceCodeVerifier, expectedState, expectedNonce })`. The `redirect_uri` comes from configuration, never from the `Host` header; the post-login target is a relative path checked against an allow-list.
- **NODE-BFF-03: Sessions live server-side behind a `SessionStore` outgoing port, backed by Redis or Postgres, never by process memory.** The port offers `get`, `set`, `compareAndSet` (atomic: it fails on a missing session or a changed generation, so two parallel refreshes cannot overwrite each other) and `destroy`. Redis implements `compareAndSet` with a Lua script; Postgres with a conditional `UPDATE … WHERE generation = $n` on its own table. Server-side state is created when a login starts (the pre-login state of NODE-BFF-02), never for plain page views. Session ids are 128 bits or more from a cryptographically secure generator (`node:crypto` or the global Web Crypto `crypto.getRandomValues`, SEC-CRY-05); where the framework signs the cookie, the signing secret (32 characters or more) comes from the secret manager and may be a list for rotation. Tokens in a shared store are encrypted at rest (SEC-CRY-03).
- **NODE-BFF-04: The session cookie is `__Host-session; Path=/; HttpOnly; Secure; SameSite=Lax`**, without `Domain`. It is cleared with the same attributes, because browsers ignore a `__Host-` cookie without `Secure`. Behind a TLS-terminating proxy the framework's proxy trust is configured, or the `Secure` cookie is never set.
- **NODE-BFF-05: The cookie holds only the session id.** Encrypted-cookie sessions that carry tokens (`iron-session` alone, Auth.js JWT sessions) are not used: tokens stay in the store (SPRING-SEC-32 intent).
- **NODE-BFF-06: Every cookie-authenticated unsafe request is CSRF-protected with the cookie and header names the frontends expect: cookie `XSRF-TOKEN`, header `X-XSRF-TOKEN`.** The token is random, bound to the session (its secret lives in the session), set after login and whenever a session starts with `Path=/; Secure; SameSite=Strict` and without `HttpOnly`, so the frontend can read it. The check reads only the header (never the body or other headers), compares in constant time (`timingSafeEqual`) and runs on every `POST`, `PUT`, `PATCH` and `DELETE`, logout included. Tests: an unsafe request without the header gets 403, with it succeeds.
- **NODE-BFF-07: Sessions have explicit lifetimes, and the tokens stay server-side.** Defaults: idle timeout 30 minutes, absolute lifetime 12 hours, never longer than the IdP session; other values in configuration with the reason in `docs/security/requirements.md`. The BFF checks both against `lastSeenAt` and `createdAt` kept in the session (cookie and store expiry only clean up). A successful login issues a new session id and drops the pre-login state and the previous session (session fixation); a failed or abandoned login leaves a live session as it was. Access tokens are refreshed with `refreshTokenGrant` shortly before expiry, once per session at a time across all instances (a lock in the shared store; waiting requests re-read the session), through `compareAndSet`, where a lost write is merged onto the newer session and retried, so a rotated refresh token is kept; idle touches do not change the generation that `compareAndSet` checks; refresh tokens live only in the store, are replaced when the IdP rotates them and end with the session. A failed refresh ends the session and answers 401, on which the frontend sends the user to the login. Tests: pre-login state is used at most once and a starting login leaves a live session intact; the session id changes at login; concurrent requests cause one refresh; a session past its idle or absolute limit is rejected (fixed clock). A page that stays open all day (a running timer) does not raise the idle timeout: its work state lives on the server, so expiry loses nothing, and the A11Y-29 warning offers to extend.
- **NODE-BFF-08: Logout ends the session in the BFF and at the IdP.** `POST /logout` (CSRF-protected): session destroyed, cookie cleared (NODE-BFF-04), refresh token revoked with `tokenRevocation` where the IdP supports it (RFC 7009), then the end-session URL `buildEndSessionUrl(config, { id_token_hint, post_logout_redirect_uri })` (RP-Initiated Logout): as `200 {"redirectUri": "…"}` when the request accepts JSON (the browser client calls logout with `fetch` because it must send the XSRF header, and `fetch` cannot follow the cross-origin redirect; it then navigates itself, TS-SEC-10), otherwise as a `303` redirect. A test covers both answers. The public back-channel endpoint accepts a `logout_token` (OIDC Back-Channel Logout 1.0; `openid-client` 6 has no helper for it) and verifies it with `jose`'s `jwtVerify` against the IdP's key set: `iss`, `aud` = client id, pinned algorithms, `iat`, `jti` (rejected when seen before its expiry), an `events` claim containing `http://schemas.openid.net/event/backchannel-logout`, `sid` or `sub` present, no `nonce`. It ends all sessions of that `sid` through an index `sid → session id` kept in the store. Tests: the old session id is rejected after logout and after a back-channel logout token for its `sid`.

## Serving the frontend

- **NODE-BFF-09: Every HTML response carries a CSP with a fresh per-response nonce; nothing caches HTML.** One nonce per response (`randomBytes(16).toString('base64')`), never reused or derived from the request. The base policy (`{n}` is the nonce): `default-src 'self'; script-src 'nonce-{n}' 'strict-dynamic'; style-src 'self' 'nonce-{n}'; connect-src 'self'; img-src 'self' data:; font-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; report-to csp; report-uri /csp-reports`, plus the Trusted Types directives and nonce placement the frontend stack names (they start in `Content-Security-Policy-Report-Only` and move to the enforced policy once the reports are clean). HTML goes out with `Cache-Control: no-store`; hashed assets with `public, max-age=31536000, immutable`. Deep links: only a `GET` that accepts `text/html` and matches no API, login or file path gets the frontend's HTML; an unknown API path or a missing file is 404, never the HTML. The report endpoint (`Reporting-Endpoints: csp="/csp-reports"`, `POST /csp-reports`) is public, limited in body size and rate, and logs each report scrubbed (directive, blocked origin, document path without query string) as a log line and a metric. `/.well-known/security.txt` (SEC-INC-02) is served explicitly. Other headers: HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, a `Permissions-Policy` that denies every feature the app does not use.

## Adoption

- **NODE-BFF-10: A Node BFF is adopted only with its threat model and tests.** Which component is the BFF and which session store it uses are recorded in the BFF ADR (NODE-BFF-01) and the product's chapter 4; that decision also covers the session store as a shared cache (RES-CCH-04). Before the first product uses it, a threat model (SEC-TM-02) covers login, callback, session store, CSRF, refresh, logout and back-channel logout, and the tests of NODE-BFF-04..09 run in CI, including an end-to-end test that the frontend's XSRF header reaches the BFF and that every header of NODE-BFF-09 is present.

- **NODE-BFF-11: The pre-login state of an anonymous caller is bounded.** Starting a login (`GET /auth/login`) is reachable without credentials, so what it stores is short-lived and capped: the pre-login record (or the session that carries it) expires after at most 10 minutes unless the callback completes, a purge job removes expired ones (RES-JOB-01), and the login start, the callback and the other public routes (back-channel logout, report endpoints) have a rate limit at the gateway or in the service (NEST-SEC-32), recorded in chapter 7. A test starts the login many times without a callback and asserts that the stored rows stay bounded after expiry and purge.
  *Why:* each anonymous request that writes a durable row fills the session store; the only limit is disk.
