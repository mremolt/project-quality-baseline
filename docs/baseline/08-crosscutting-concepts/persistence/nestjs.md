# NestJS: Persistence with PostgreSQL

Database, Kysely, transactions and migrations for NestJS services (default NEST-D: Kysely with `pg`, Kysely migrator). It implements the shared rules on mapping ([mapping-between-boundaries.md](../mapping/mapping-between-boundaries.md)), transactions (ARCH-UC-11, RES-TX-*), N+1 ([avoiding-n-plus-one.md](../api/avoiding-n-plus-one.md)) and migrations at deploy time (REL-DB-* in [delivery-and-release.md](../../07-deployment-view/delivery-and-release.md)). Pool timeouts and size: NEST-RES-01/04 in [../resilience/nestjs.md](../resilience/nestjs.md). Bind parameters and `sql.raw`: NEST-SEC-25 in [../security/nestjs-hardening.md](../security/nestjs-hardening.md). Running migrations in a deployment: [nestjs-delivery.md](../../07-deployment-view/nestjs-delivery.md).

Files (in `backend/src/platform/adapter/out/persistence/` unless noted):

| File | Content |
|---|---|
| `database.ts` | the one `pg.Pool` and `Kysely<DB>` of the process |
| `generated/db.ts` | table types generated by `kysely-codegen` (NEST-DB-05) |
| `kysely-transaction.adapter.ts` | `TransactionPort` implementation, `isInTransaction()` (NEST-DB-08) |
| `cluster-lock.ts` | lock helper for jobs (NEST-RES-11) |
| `migrations/` | `YYYY-MM-DDTHHmm_<name>.ts` files and `index.ts` (the static list) |
| `migrator.ts` | `migrateToLatest()` and `assertSchemaCurrent()` |
| `src/platform/ports/out/transaction.port.ts` | the `TransactionPort` interface; its token in `src/platform/platform.tokens.ts` |

## Rules

### Engine and schema

- **NEST-DB-01: PostgreSQL 18 is the engine, in the same major version everywhere** (production, `compose.yaml`, Testcontainers). Local and test images are Debian-based (`postgres:18`), not Alpine: Alpine's libc sorts and compares text differently.
- **NEST-DB-02: Schema conventions:** names `snake_case`, tables plural (`orders`, `order_lines`); ids `uuid` generated by the application (`randomUUID()`) or `bigint` from a sequence; instants `timestamptz`; money and decimals `numeric(p,s)`, never `real`/`double precision`; enums `text` with a check constraint; constraints (keys, `NOT NULL`, unique, check, foreign keys) live in the database, application validation does not replace them.
- **NEST-DB-03: Types cross the driver without loss.** `pg` returns `numeric` and `bigint` (`int8`) as strings: keep them as strings in the row type and map them to the domain's decimal or id type in the adapter (API-REST-01: decimals stay strings to the API). `timestamptz` arrives as a JS `Date` (an instant); never use `timestamp` without time zone for instants. No global `pg.types.setTypeParser` that turns `numeric` into `number`.

### Kysely in the adapter

- **NEST-DB-04: One `Kysely<DB>` instance and one `pg.Pool` per process,** created in `database.ts` from the database config schema and provided by the platform persistence module; `onApplicationShutdown` calls `db.destroy()`. Pool `max`, `connectionTimeoutMillis`, `statement_timeout`, `transaction_timeout` and the two `error` listeners follow NEST-RES-01/04; `idle_in_transaction_session_timeout` (same value as `transaction_timeout`) ends a session that waits inside a transaction. Persistence adapters never inject the `Kysely` instance or the pool: they get the executor from the transaction adapter (NEST-DB-08). The `Kysely` token lives in its own file that only `src/platform/adapter/out/persistence/` imports (dependency-cruiser rule).

  | Key (NEST-CFG-05) | Meaning |
  |---|---|
  | `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME` | server and database |
  | `DATABASE_USER`, `DATABASE_PASSWORD` (secret, `_FILE`) | DML user of the application pool |
  | `DATABASE_MIGRATION_USER`, `DATABASE_MIGRATION_PASSWORD` (secret, `_FILE`) | DDL user; set only where the service migrates at start-up |
  | `DATABASE_POOL_MAX`, `DATABASE_CONNECTION_TIMEOUT_MS`, `DATABASE_STATEMENT_TIMEOUT_MS`, `DATABASE_TRANSACTION_TIMEOUT_MS` | NEST-RES-01/04 |
  | `DATABASE_MIGRATION_LOCK_TIMEOUT_MS` (5000), `DATABASE_MIGRATION_STATEMENT_TIMEOUT_MS` (120000) | NEST-DB-16 |
- **NEST-DB-05: Table types are generated from the migrated schema, never written by hand.** `generated/db.ts` is the output of `kysely-codegen --dialect postgres --exclude-pattern 'kysely_*' --print` against a database migrated with the real migrations, committed. An integration test (`db-schema.it.test.ts`) starts Testcontainers PostgreSQL, runs the migrations, runs `kysely-codegen` and compares with `await expect(stdout).toMatchFileSnapshot('./generated/db.ts')`; `npm run test:it -- -u` regenerates it. Snapshots are not written on CI, so a drifted file fails the build.
  *Why:* this is the check that the code's view of the schema matches the migrations. Hand-written interfaces drift silently (a nullable column typed as non-null compiles and fails at runtime).
- **NEST-DB-06: Rows never cross a port; persistence always uses two-way mapping** (ARCH-MAP-02/03 tightened, like the JPA rule of the Java stack). The adapter maps `Selectable<Orders>` rows to domain types and back in plain functions next to the adapter (ARCH-MAP-08). Read-only query ports may select straight into the port's result type inside the adapter. Each adapter narrows the instance to its own tables with `executor().$pickTables<'orders' | 'order_lines'>()`, so a query on another context's table does not compile.
- **NEST-DB-07: Queries are built with Kysely's builder or the `sql` template tag, values always as bind parameters** (NEST-SEC-25). Dynamic identifiers and sort columns come from an allow-list (API-REST-09). `sql.raw` and `sql.lit` are banned by ESLint (`no-restricted-properties` on `sql.raw` and `sql.lit`).

### Transactions (ARCH-UC-11, RES-TX)

- **NEST-DB-08: The use case sets the boundary with `TransactionPort.runInTransaction(work)`; the Kysely adapter keeps the open transaction in `AsyncLocalStorage`.** `application` imports only the port (NEST-ARCH-08). The adapter runs `work` inside `db.transaction().execute()` and `AsyncLocalStorage.run(trx, work)`; persistence adapters call `executor()`, which returns the open transaction of the current async context or the pool outside one. A nested `runInTransaction` joins the outer transaction. `isInTransaction()` (exported from the same file) is what the HTTP guard of NEST-RES-03 asks.

```ts
// src/platform/adapter/out/persistence/kysely-transaction.adapter.ts
const current = new AsyncLocalStorage<Transaction<DB>>();
export const isInTransaction = (): boolean => current.getStore() !== undefined;
const RETRYABLE_SQLSTATE = new Set(['40001', '40P01']);           // serialization failure, deadlock
const MAX_ATTEMPTS = 3;                                            // code, not configuration (CFG-01)

@Injectable()
export class KyselyTransactionAdapter implements TransactionPort {
  constructor(@Inject(KYSELY) private readonly db: Kysely<DB>) {}

  async runInTransaction<T>(work: () => Promise<T>): Promise<T> {
    if (current.getStore()) return work();                         // nested: join
    for (let attempt = 1; ; attempt++) {
      try {
        return await this.db.transaction().execute((trx) => current.run(trx, work));
      } catch (err) {
        const retryable = err instanceof ConcurrentModificationError || RETRYABLE_SQLSTATE.has((err as { code?: string }).code ?? '');
        if (!retryable || attempt >= MAX_ATTEMPTS) throw toPortError(err);
        await setTimeout(Math.random() * 50 * attempt);             // jitter (node:timers/promises)
      }
    }
  }

  executor(): Kysely<DB> {
    return current.getStore() ?? this.db;
  }
}
```

  Kysely logs `begin` and `commit` as statements (relevant for NEST-DB-12). The transaction adapter is a platform adapter shared by all contexts; context modules inject `TRANSACTION_PORT`.
- **NEST-DB-09: A conflict re-runs the whole unit of work** (RES-RTY-02): the transaction adapter retries `work` in a new transaction on `ConcurrentModificationError` (the optimistic-lock error, a `ConflictError` subclass in `src/platform/domain`) and on SQLSTATE `40001`/`40P01`, at most 3 attempts with jitter, only for the outermost call. Remote calls are never inside `work` (RES-TX-01), so a re-run repeats only database work. When attempts run out the `ConflictError` reaches the caller (409, API-REST-11). The consumer's error handling retries what is left (RES-RTY-04 counts this re-run as part of the database layer, not as a second retry of the remote call).
- **NEST-DB-10: Optimistic locking uses a `version integer not null default 0` column** on aggregates that users change concurrently. The update is `update … set …, version = version + 1 where id = $1 and version = $2`; `numUpdatedRows === 0n` throws the context's `ConcurrentModificationError` subclass (`OrderModifiedConcurrentlyError`). The version travels in the domain type and to the API (API-REST-11).
- **NEST-DB-11: Driver errors are mapped in the adapter, never passed through the port** (ARCH-ADP-01): pg's pool wait timeout (a plain `Error` with the message `timeout exceeded when trying to connect`) becomes `UnavailableError` (NODE-ARCH-07; the REST filter answers 503 with `Retry-After`); a unique violation (`23505`) that the use case expects becomes the port's `ConflictError`; anything else stays a technical error (500). A session ended by `transaction_timeout` or `idle_in_transaction_session_timeout` rejects with `Connection terminated unexpectedly` or `Client has encountered a connection error and is not queryable` (no SQLSTATE): technical error.

### Loading data (API-N1)

- **NEST-DB-12: No query per item.** Kysely has no lazy loading, so N+1 shows up as a loop of queries: an `await` inside `for`/`map` over rows is a defect. Load children with one `where('order_id', 'in', ids)` query per child table (or a join) and group in memory; every query and batch port has a fixed statement count. Persistence integration tests assert it with Kysely's `log` option (`log: (e) => { if (e.level === 'query') statements.push(e.query.sql); }`), excluding `begin`/`commit`: loading 3 orders with their lines is exactly 2 statements (API-N1-05/06).
- **NEST-DB-13: Every collection query is bounded in the query itself** (API-REST-08, API-N1-07): `limit(size).offset(page * size)` with the capped `size` for page paging, or keyset paging (`where (created_at, id) > ($1, $2) order by created_at, id limit $3`) for cursor paging; the order always ends with the id as tiebreaker (API-REST-09). An unpaged query has a hard `limit` documented on the port.

### Migrations (decision NEST-D, REL-DB)

- **NEST-DB-14: Migrations are TypeScript files run by `Migrator` from `kysely/migration`** (not from `kysely`, 0.29 moved it), listed statically in `migrations/index.ts` (no `FileMigrationProvider`, so `dist/` needs no directory scan), with `allowUnorderedMigrations: false`. Names are `YYYY-MM-DDTHHmm_<kebab-name>.ts`; the key in the list is the name without `.ts`. Each file exports only `up(db: Kysely<unknown>)`: migrations are forward-only, there is no `down` (REL-RB-03). Migrations use `db.schema` or the `sql` tag, never the application's table types (they change later).
- **NEST-DB-15: What the Kysely migrator does on PostgreSQL** (Kysely 0.29.9, verified): it takes a session-level `pg_advisory_lock` with a fixed id and sets `lock_timeout` to one hour for that statement only, so parallel instances wait instead of migrating twice (REL-DB-03); it runs **all pending migrations of one run in one transaction** (one failure rolls back all of them); it fails when a migration sorts before the last executed one (`corrupted migrations`) or when an executed migration is missing from the list; it records runs in `kysely_migration` and `kysely_migration_lock`. `migrateToLatest()` never throws: `migrator.ts` throws its `error`.
- **NEST-DB-16: The migration connection is its own one-connection pool with the DDL user and two session timeouts:** `lock_timeout` (default 5 s, REL-DB-03: DDL waiting for a busy table fails instead of blocking traffic) and `statement_timeout` (the migration budget, default 120 s, REL-DB-04), passed as pg connection options. `statement_timeout` is also the bound on the wait for the advisory lock (Kysely's own lock wait is one hour), so it is the bounded retry of REL-DB-03 and must fit the start-up budget (REL-RUN-04).
- **NEST-DB-17: Two database users** (REL-DB-01): the DDL user owns the schema (not a superuser) and is used only by the migration; the application's pool uses a DML-only user. The first migration grants the DML user `USAGE` on the schema, `ALTER DEFAULT PRIVILEGES … GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES` and `… GRANT USAGE, SELECT ON SEQUENCES`, and `SELECT` on `kysely_migration` (for NEST-DB-18). The DML user's name is `DATABASE_USER`, passed to the migration connection as an option (`-c app.runtime_role=<DATABASE_USER>`, read in the migration with `current_setting('app.runtime_role')` and quoted with `sql.id`), so no user name is written into a migration. Default privileges cover tables the DDL user creates later.
- **NEST-DB-18: `assertSchemaCurrent()`** compares the static list with `migrator.getMigrations()` (each entry has `executedAt`) using the DML user, and throws when a migration is pending. Instances use it when they do not migrate themselves (pre-deploy variant, NEST-REL rules in [nestjs-delivery.md](../../07-deployment-view/nestjs-delivery.md)).
- **NEST-DB-19: Migrations are immutable once on `main`, checked in CI.** Kysely keeps no checksums, so `scripts/check-migrations.mjs` (part of `npm run verify`, run with the base branch fetched) fails when `git diff --name-status --no-renames origin/main...HEAD -- src/platform/adapter/out/persistence/migrations` shows any status other than `A` (except `index.ts`), when a new file does not match the name pattern, or when a new name sorts before the newest name on `origin/main` (`git ls-tree`). A fix is a new migration.
- **NEST-DB-20: Migrations are compatible with the previous release** (expand/contract, REL-DB-02): add columns nullable or with a default, write both forms, migrate data in a background job of the new version (REL-DB-04), drop in a later release. Destructive statements are linted (REL-DB-06) and need a note in the pull request. Data migrations over large tables are never a migration.
- **NEST-DB-21: `CREATE INDEX CONCURRENTLY` cannot run in the default transactional run** (it fails with SQLSTATE `25001`). A product that needs it on a large table runs the migrator with `migrateToLatest({ disableTransactions: true })` for the whole product, and then every migration wraps its statements in `db.transaction()` itself and is written to be re-runnable (`if not exists`), because a failure between the migration and its record leaves it to run again. This is a product decision recorded in chapter 8; without it, index creation on large tables waits for a low-traffic window with `lock_timeout`.

### Tests

- **NEST-DB-22: Every persistence test runs the real migrations against Testcontainers PostgreSQL** (`@testcontainers/postgresql`, image `postgres:18`) as `*.it.test.ts`, with the DDL and DML users created in the container, the migrations run as the DDL user and the adapter run as the DML user. Required cases per adapter: round trip of every mapped column (decimal precision, instants), optimistic-lock conflict, statement count of query and batch ports (NEST-DB-12), and the error mapping of NEST-DB-11. The platform has one test each for: rollback of all adapter writes when `work` rejects, other connections not seeing uncommitted rows, nested join, two concurrent `runInTransaction` calls getting different transaction ids, the conflict retry, the generated types (NEST-DB-05) and the migrator behaviour of NEST-DB-15/16.

## Agent checklist

- [ ] New table or column: migration added (name pattern, `up` only, listed in `index.ts`), previous release still works, `generated/db.ts` regenerated?
- [ ] Types per NEST-DB-02/03: `numeric` and `int8` as strings, instants `timestamptz`, constraints in the migration?
- [ ] Adapter uses `executor()` and `$pickTables`, maps rows both ways, never returns a row type through a port?
- [ ] Use case work wrapped in `runInTransaction`; no remote call inside; conflicts thrown as `ConcurrentModificationError`?
- [ ] Driver errors mapped (`UnavailableError`, conflict) in the adapter (NEST-DB-11)?
- [ ] No query in a loop; statement count asserted; collection queries limited in SQL (NEST-DB-12/13)?
- [ ] No edit to a migration on `main`; `check-migrations` green (NEST-DB-19)?
