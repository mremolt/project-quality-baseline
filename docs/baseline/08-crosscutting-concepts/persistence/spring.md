# Spring Boot: Persistence with PostgreSQL

Database engine, migrations and Hibernate settings for services with PostgreSQL. Adapter structure, mapping strategy and transactions are in [05-building-block-view/spring.md](../../05-building-block-view/spring.md) (SPRING-ARCH-07, -09, -10, -11, -16); this doc adds the database-side rules and the choice between JPA and `JdbcClient` (SPRING-DB-15).

## Rules

### Engine and migrations

- **SPRING-DB-01: PostgreSQL is the engine, in the same major version everywhere** (production, local Compose, Testcontainers). Local and test images are Debian-based (`postgres:18`), not Alpine: Alpine's libc sorts and compares text differently from production.
- **SPRING-DB-02: Flyway owns the schema.** Dependencies: `spring-boot-starter-flyway` **and** `org.flywaydb:flyway-database-postgresql` (SPRING-LIB-01). SQL files `V<n>__<description>.sql` in `src/main/resources/db/migration` (Flyway's default location; resources have no Java package, so migrations belong to the service, not to one adapter). `spring.jpa.hibernate.ddl-auto=validate`: Hibernate never changes the schema.
- **SPRING-DB-03: `spring.jpa.open-in-view=false`.** A lazy-loading exception in a controller means an entity leaked through a port (SPRING-ARCH-09); the fix is in the adapter, not in a wider session.
- **SPRING-DB-04: Migrations are immutable once merged.** Fixes are new versions. Repeatable migrations (`R__`) only for views and functions.
- **SPRING-DB-05: Migrations are backward compatible with the previous release** (expand/contract): during a rollout the old backend instance and the old frontend still run (REPO-API-02). Add the column nullable or with a default, deploy code that writes both, migrate data, remove the old column in a later release. Destructive changes (drop, rename, type change) need an explicit note in the pull request. Shared rule: REL-DB-02 ([delivery-and-release.md](../../07-deployment-view/delivery-and-release.md)).
- **SPRING-DB-06: Long-locking DDL is reviewed for Postgres specifics:** `CREATE INDEX CONCURRENTLY` (outside a transaction: `executeInTransaction=false` for that file, and Flyway's transactional lock switched off, `spring.flyway.postgresql.transactional-lock=false`, SPRING-REL-04), `NOT VALID` then `VALIDATE CONSTRAINT`, no table rewrites on large tables without a plan. Every migration connection runs with a `lock_timeout` (SPRING-REL-02).

### Schema conventions

- **SPRING-DB-07: Names are `snake_case`, tables plural** (`orders`, `order_lines`). An entity named `Order` needs an explicit `@Table(name = "orders")`: the default table name `order` is a reserved word in SQL. Boot's default naming strategy maps camelCase fields to snake_case columns; no custom `@Column(name)` needed for the common case.
- **SPRING-DB-08: Types:** identifiers `uuid` (application-generated) or a `bigint` from a sequence (not `IDENTITY` where batching matters); instants `timestamptz` (maps to `Instant`/`OffsetDateTime`); money and decimals `numeric(19,2)` or with the scale the domain requires, never `float`/`double` (matches the decimal-string JSON rule, API-REST-01, SPRING-REST-04); enums `text` with a check constraint (never ordinals).
- **SPRING-DB-09: Constraints live in the database** (primary and foreign keys, `NOT NULL`, unique, check). Application validation is not a substitute.
- **SPRING-DB-10: Optimistic locking with `@Version`** on aggregates that users update concurrently. Status mapping of a lock failure: SPRING-REST-12 and the status table in API-REST-06 ([rest-conventions.md](../api/rest-conventions.md)). With two-way mapping the version travels as data: the domain record carries `version`, the mapper copies it, and the adapter rejects a write whose version differs from the stored one with the domain's conflict exception before Hibernate's own check. Hibernate also increments `@Version` when a collection of the entity changes, so a freshly inserted aggregate with children can already be version 1: a use case that writes the same aggregate twice (insert, then link an external id) reloads it between the writes, and adapter ITs compare aggregates ignoring the version.

### JPA specifics (inside `adapter.out.jpa`)

- **SPRING-DB-11: Entities have no Lombok, protected no-arg constructor, no public setters.** `equals`/`hashCode` are chosen deliberately (by business key or by assigned id; never over lazy associations). Details: the `java-hibernate-jpa` skill. This applies to the entity, which is not the domain model when two-way mapping is used (SPRING-ARCH-10).
- **SPRING-DB-12: Query ports are bounded.** Every collection query is paged with a capped page size, or has a documented hard upper bound that the query itself enforces (`LIMIT`, `setMaxResults`) (API-REST-08, API-N1-07, SPRING-REST-11). Statement counts are asserted in adapter tests ([08-crosscutting-concepts/testing/spring.md](../testing/spring.md)).
- **SPRING-DB-13: Native SQL and `JdbcClient` are fine** where JPA adds nothing (ARCH-ADP-13), inside the adapter, with the same tests. Values only as bind parameters; identifiers and `ORDER BY` from an allow-list (SPRING-SEC-31). jOOQ or Spring Data JDBC are allowed in an adapter under the same rule; no ADR needed while the choice stays inside the adapter.

### Testing

- **SPRING-DB-14: Every persistence test runs the real migrations against a Testcontainers PostgreSQL** (SPRING-TEST-05). Mapping and migration are tested together, so a missing migration fails the test, not production.
- **SPRING-DB-19: Privilege tests run as the non-superuser DML role, never as the Testcontainers user.** The Testcontainers user is a superuser and passes every `UPDATE` on an append-only table (SEC-AUD-01, SPRING-SEC-27). The shared test infrastructure creates the DML role (`CREATE ROLE app LOGIN PASSWORD …`, no superuser, no ownership), runs the migrations with the container user so the grants of SPRING-REL-03 apply to it, and the privilege test opens a connection as that role and asserts that `UPDATE` and `DELETE` on the append-only tables fail with SQL state `42501` (insufficient privilege) while `INSERT` succeeds. Reading `information_schema.role_table_grants` alone is not enough: it does not prove the effect.
  *Why:* a grant test as superuser is green whatever the grants say.

### Persistence technology (default SPRING-D4)

- **SPRING-DB-15: Spring Data JPA plus `JdbcClient` is the default.** JPA for aggregates that are loaded and changed as a whole: one query with `left join fetch` (API-N1-05), dirty checking, `@Version`. `JdbcClient` for read models, reporting queries, bulk updates and tables without aggregate invariants (reference rows, markers, dated rows such as contracts or holidays, period locks) where Hibernate's session, proxies and flush behaviour add nothing. A JPA adapter may run `JdbcClient` queries for its own aggregate inside `adapter.out.jpa`; an adapter built only on `JdbcClient` lives in `adapter.out.jdbc` ([05-building-block-view/spring.md](../../05-building-block-view/spring.md)). Both use the same port, mapping and statement-count tests (SPRING-DB-12, SPRING-TEST-06). Spring Data JDBC and jOOQ stay possible inside an adapter (SPRING-DB-13). If Spring Data JPA and Spring Data JDBC repositories are both on the classpath, Spring Data switches to strict repository configuration mode; then each adapter's `@Configuration` declares its scan explicitly (`@EnableJpaRepositories(basePackages = "…adapter.out.jpa")`, `@EnableJdbcRepositories(basePackages = "…adapter.out.jdbc")`, SPRING-ARCH-05).
  *Why:* JPA pays off where whole aggregates are loaded and written with optimistic locking. Elsewhere its session, proxy and flush behaviour (lazy loading, dirty checking, cascades) is a frequent source of bugs, while a plain SQL query with a row mapper is easier to read, review and count.
- **SPRING-DB-16: Invariants across rows are enforced in PostgreSQL, atomically (ARCH-UC-16).** In order of preference, as far as the domain allows it: a constraint (a partial unique index such as `UNIQUE (user_id, work_date, project_id) WHERE deleted_at IS NULL` with `INSERT … ON CONFLICT`, an exclusion constraint, a foreign key); a conditional write (`UPDATE … WHERE id = :id AND <condition>`) whose row count the adapter checks; `SELECT … FOR UPDATE` on the row the invariant hangs on; `pg_advisory_xact_lock(<key>)` taken in both the check and the conflicting write when no row exists to lock (for example per user and month); where many commands check and one rare change conflicts with them (closing a period), the commands take `pg_advisory_xact_lock_shared(<key>)` and the change takes the exclusive lock, so commands do not serialize each other, and the test proves both orders (a change waits for a command in flight; a command started during a change waits and then sees it). Queue rows are claimed with `FOR UPDATE SKIP LOCKED` or a status update before the work starts. Counts of rows: SPRING-DB-22; upserts: SPRING-DB-23. The adapter maps the resulting violation to a `ConflictException` (SPRING-DB-18). The use case still checks first (`existsById`) for the clean error and the early exit; the constraint is the guard against the race, and both paths end in the same error code. A constraint is only right when it forbids exactly the states the domain forbids: where the domain allows several rows per key (several bookings in one cell of a timesheet), a unique index would reject valid data, so the invariant is held by a lock instead, and the use case's comment says why. The concurrency test is an `*IT` against Testcontainers that runs the two conflicting operations as two real transactions in a controlled order: the first does its check and write and is held open (a latch) until the second has reached the conflicting statement; the test asserts that the second fails with the mapped exception or, for a lock, is seen waiting and proceeds after the commit, and that exactly one effect remains. It is run against the code without the mechanism once, to see it fail. Repeating a race of two free-running threads many times is not a substitute, because it fails only by chance.
- **SPRING-DB-22: A rule over a count of other rows locks before it counts** (ARCH-UC-16, SPRING-DB-16). Example: "at least one active administrator remains". Every command that can lower the count takes `pg_advisory_xact_lock(<constant key>)` as its first statement, or locks the counted rows with `SELECT … FOR UPDATE`, before it counts. The concurrency IT of SPRING-DB-16 runs two such commands against each other.
  *Why:* under READ COMMITTED two commands otherwise both see "two admins" and both commit (write skew).
- **SPRING-DB-23: `INSERT … ON CONFLICT DO UPDATE` is used only where overwriting is the domain's intent.** Where the domain tells "create" from "change" (an absence already recorded for that day), the use case reads the existing row first and either refuses or records a change. An upsert keeps the existing row's id, so the adapter returns the stored id and the old values (`RETURNING`) for the audit entry, and never an id the use case generated for a row that was not inserted.
- **SPRING-DB-17: Every adapter query on a table that grows has an index for its filter and sort columns, and every foreign-key column is indexed** (PostgreSQL does not index foreign keys itself). An `OR` across two columns becomes a `UNION ALL` of two indexed queries. The pull request that adds a query names the index it uses, or why a scan is fine (small, bounded table). Append-only tables (audit, history) get these indexes from the start, because they only grow. Indexes on existing large tables are created with `CREATE INDEX CONCURRENTLY` in their own migration (SPRING-REL-02).
  *Why:* a missing index is invisible on test data and turns into statement timeouts (RES-TMO-04) years later.
- **SPRING-DB-18: Constraint violations are mapped by constraint name, never by message text.** After a violation PostgreSQL has aborted the transaction (`25P02`: every further statement fails) and the Hibernate session is unusable, so the adapter decides the meaning from the exception alone: the constraint name, the SQLState, or data the use case loaded before the write. It issues no further query to find out which case it was (or it runs the write in a savepoint). The integration test for each mapping runs inside a transaction, as the use case does; a test without one cannot see this failure. A JPA adapter reads the name from Hibernate's `org.hibernate.exception.ConstraintViolationException.getConstraintName()` in the cause chain of the `DataIntegrityViolationException`; the PostgreSQL driver stays a runtime dependency (compiling against `PSQLException` drags an annotation jar into `-Werror` builds). Where no name is available (an exclusion constraint, SQLState `23P01`, for which Hibernate reports `null`; a `DuplicateKeyException` from a `JdbcClient` statement), the adapter maps by SQLState (`SQLException.getSQLState()` of the most specific cause) only where the statement can violate exactly one such constraint, and says so at the mapping. One shared helper maps to a business exception with a stable code (ARCH-UC-13) and keeps the original exception as the cause. Constraint names are explicit in the migrations, so a rename is a visible change.
- **SPRING-DB-21: Optional filters build their `WHERE` clause from the filters present, and listings of growing append-only tables page by keyset.** A query with optional filters appends one fixed SQL fragment per filter that is set, each with bind parameters (SPRING-SEC-31). It does not use the catch-all form `(:p IS NULL OR col = :p)`: after a few executions pgjdbc switches to server-side prepared statements, PostgreSQL may then choose a generic plan that uses none of the filter's indexes, and every call scans the table. A listing of an append-only or fast-growing table (audit log, security events, history) pages by keyset (`where (occurred_at, id) < (:lastAt, :lastId) order by occurred_at desc, id desc limit :n`, cursor paging of API-REST-08) and does not run an exact `count(*)` per page. A total, if the screen needs one, is capped or estimated.
  *Why:* both patterns are fast on test data and degrade with every row. The query's cost grows with a table that is never purged, until the statement timeout turns the page into errors.
