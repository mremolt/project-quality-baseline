# Internationalization (i18n)

Rules for products that support more than one language. They apply to every stack; each stack adds its rules in `<stack>.md` here (backends: [spring.md](spring.md), [nestjs.md](nestjs.md); frontends: Per stack line at the end). Whether a product is multilingual is a project decision (I18N-01); a single-language product ignores this topic except for I18N-02 and I18N-03, which cost nothing.

**Terms.** *Translate* means choosing the words for a UI string. *Format* means rendering dates, numbers and money for a locale. They have different owners (table below).

## Decisions

Decided for the baseline on 2026-11-20:

| Topic | Decision |
|---|---|
| Frontend mechanism | Runtime translation with the stack's i18n library, one build for all languages. Build-time translation only through an ADR, for single-language deployments |
| Catalogs | Nested JSON per language and scope |
| Translation management | **Weblate, self-hosted**, one shared instance for all products, on our own infrastructure. Constraint: self-hosted open source, no subscription or license fees. Tolgee (paid review, QA, shared TM and glossary; 10-seat cap) and hosted proprietary services are out |
| Machine translation | Self-hosted only (LibreTranslate or Ollama); a draft source, reviewed by a person. Paid hosted MT is out |
| Source locale | `en`, also the last fallback, unless the product's audience and writers are German (then recorded in the product ADR) |
| Language persistence | Profile on the backend for signed-in users, browser storage for anonymous ones |
| URL | No locale in the URL for authenticated apps; a path prefix only for public SEO pages (then server rendering, recorded with the product's rendering decision) |
| RTL | Not supported; CSS logical properties are required, and a nightly, non-blocking pseudo-RTL run (TEST-I18N-02) shows where the option would break |
| Backend error text | Stable codes plus localized text as a fallback (SPRING-I18N-02, NEST-I18N-04) |
| User-authored multilingual content (product names, descriptions) | **Out of scope for the baseline.** Products solve it themselves; it never goes into the UI catalog or Weblate |
| Release-blocking locales | Per product, in its ADR |

## Who does what

| Topic | Rule of thumb | Owner |
|---|---|---|
| Words (labels, messages, errors) | Key plus catalog, ICU for plural/select/gender | Frontend catalog (translators) |
| Dates, times | UI formats from UTC ISO-8601 with the active locale and the user's time zone | Frontend |
| Numbers, money | UI formats the decimal string with `Intl.NumberFormat`; an amount never passes through a JS `number` | Frontend |
| Plurals | ICU `{count, plural, one{…} other{…}}`, never `count === 1` in code | Catalog |
| Sorting | Client-side lists: `Intl.Collator(locale)`. Server-paged lists: the server decides the order with a defined collation, the UI does not re-sort a page | Backend for paged data, frontend otherwise |
| Enums | The API sends the enum string (SPRING-REST-06, NEST-REST-12); the UI maps it to the key `enum.<type>.<value>` | Frontend |
| Time zone | Instants are shown in the user's zone; date-only values (`yyyy-MM-dd`) have no zone and are never converted | Frontend |
| Emails, PDFs, push, exports made by the server for people | Rendered in the recipient's stored language | Backend (outgoing adapter) |
| Files for import into another system (payroll, accounting) | One fixed format chosen by the consumer, never localized ([EXP-01](../exports/file-exports.md)) | Backend (outgoing adapter) |

## Rules

- **I18N-01: i18n is a project decision recorded as an ADR:** supported locales, source locale, fallback chain, who translates, release-blocking locales, and build-time or runtime translation.
  *Why:* it shapes build, test and deployment, like the rendering strategy.
- **I18N-02: Domain, ports and use cases contain no UI text.** They carry stable codes and parameters; adapters translate (extends ARCH-ORG-05, ARCH-ADP-05).
  *Why:* text is a presentation concern and changes with the language.
- **I18N-03: The API contract stays language-neutral.** Decimals as strings, instants in UTC, dates as `yyyy-MM-dd`, enums as strings ([API-REST-01..03](../api/rest-conventions.md)); the server never formats values for display.
  *Why:* one contract serves every locale and client.
- **I18N-04: Locale tags are BCP 47** (`de`, `de-CH`, `en-GB`). Catalogs and bundles use the same tags, and there is one list of supported locales per product, shared by frontend, backend and the translation tool.
  *Why:* avoids `de_DE` versus `de-DE` mismatches.
- **I18N-05: The source locale is the only hand-written catalog;** all other locales come from the translation tool.
  *Why:* one writing path, no merge fights.
- **I18N-06: The user's language is a user setting.** Resolution order: explicit choice (profile or storage), then `Accept-Language`, then the default. The frontend sends the active language to the backend as `Accept-Language`.
  *Why:* one rule on both sides.
- **I18N-07: No string concatenation, no plural logic in code, no word-order assumptions.** Use placeholders and ICU.
  *Why:* grammar differs per language.
- **I18N-08: Every key has translator context:** a description and a maximum length where it matters. UI strings SHOULD also have a screenshot.
  *Why:* "Open" can be a verb or an adjective.
- **I18N-09: Fallback chain** `user locale` → `language only` (`de-CH` → `de`) → source locale. A missing key logs a warning and shows the fallback text, never the raw key.

## Tooling and workflow

- **TOOL-I18N-01: Weblate (self-hosted) is the translation tool** unless the product ADR chooses another that meets the same constraint (self-hosted open source, no fees). One shared instance serves all products; sizing and setup follow Weblate's installation docs (PostgreSQL 15+, Valkey/Redis, Celery workers, SMTP; at least 3 GB RAM).
- **TOOL-I18N-02: Translations flow through Git.** Weblate writes to an `l10n` branch and opens pull requests that are merged with merge commits (not squash, per Weblate's guidance); people do not edit non-source catalogs by hand. CI runs the same gates on these pull requests.
  *Why:* one writer per file.
- **TOOL-I18N-03: CI fails on any of these catalog errors:** keys used in code but missing in the source catalog, unused keys, invalid JSON or duplicate keys, placeholder or ICU mismatches between source and target, and keys without context.
  *Why:* gates beat reviews.
- **TOOL-I18N-04: A pseudo-locale (accented, expanded, bracketed text) is generated from the source catalog and used in development and tests only.** It is generated with an existing npm package (selected after a license and maintenance review, see [chapter 11](../../11-risks-and-technical-debt/README.md#verify-before-first-use)) and is never shipped. The pseudo-RTL locale of TEST-I18N-02 is generated the same way (text mirrored with bidi control characters, `dir="rtl"`).
  *Why:* finds hard-coded text and layout breaks without translators.
- **TOOL-I18N-05: Release rule.** Every locale marked release-blocking is 100 percent translated and reviewed when the release is cut (release branches: [REL-BR-04](../../07-deployment-view/delivery-and-release.md)); other locales ship with the fallback and are listed in the release notes. Strings freeze about three working days before the cut (team may adjust); the Weblate component is locked while the `l10n` pull request merges.
- **TOOL-I18N-06: Machine translation is a draft source only.** A person reviews every suggestion before the string is approved. Customer data never goes to a hosted MT service without an ADR and data-protection sign-off (hosted paid MT is already excluded by the decision above).
- **TOOL-I18N-07: Translator context is kept in a sidecar `context.json` next to each catalog** and pushed to Weblate by CI (descriptions, max lengths, screenshot names).
  *Why:* context lives in Git, reviewable with the code that adds the key.
- **TOOL-I18N-08: Until the translation tool is connected, non-source catalogs are written in the repository, with context, and every string written by an agent or machine translation is marked for human review.** The product records the interim state in an ADR (when the tool will be connected, who reviews); the marker (e.g. a `"review": true` entry in `context.json`) is cleared only by a person, and no release-blocking locale ships with markers left (TOOL-I18N-05). The catalog checks of TOOL-I18N-03 run from the first commit.

### Workflow

1. **Developer:** adds keys with source text (source locale only) and context in the feature scope; runs the local gate `npm run i18n:check` (TOOL-I18N-03); checks the layout in the pseudo-locale; the review checks the I18N rules.
2. **CI:** `i18n:check` on every pull request; locale Playwright projects (source and pseudo on pull requests, the full set on main, pseudo-RTL nightly and non-blocking); the backend bundle parity test.
3. **Translators (Weblate):** a webhook from the Git host triggers a pull when source catalogs change; new or changed sources appear as to-do; reviewers approve (suggestions and voting); screenshots from Playwright runs are uploaded through the API; a glossary holds product terms.
4. **Changing source text:** typos are edited in place; a changed meaning gets a new key (keys are stable semantic ids, never the source sentence).
5. **Release:** merge the `l10n` pull request, build once, deploy the single artifact.

## Tests

- **TEST-I18N-01: Component tests render with the real source-locale catalog** so role-and-name queries stay readable (TS-TEST-07); tests never assert keys.
  *Why:* tests describe what users read.
- **TEST-I18N-02: Playwright has locale projects:** the source locale, one other Latin locale with long text (for example `de-DE`), and the pseudo-locale. Each project sets `locale` and `timezoneId`. A generated pseudo-RTL locale (TOOL-I18N-04) runs the main screens nightly; it is reported, never blocking, because RTL is not supported (decision table).
  *Why:* formatting and layout differ per locale; the pseudo-RTL run shows where CSS logical properties (UI-09) are missing before a product ever needs RTL.
- **TEST-I18N-03: axe (TS-TEST-12) runs per locale project and asserts `html[lang]` and `dir` after a switch** (WCAG 3.1.1): it asserts that `html[lang]` equals the active language and `dir` matches it after a switch (`ltr` for every supported locale, `rtl` only in the pseudo-RTL run) (WCAG 3.1.1).
- **TEST-I18N-04: An overflow check runs on the main screens in the pseudo-locale:** no horizontal page scroll (UI-10), no clipped text where the design forbids truncation.
- **TEST-I18N-05: Backend contract tests send `Accept-Language` for each supported locale and for an unsupported one** and assert that `code` is identical while `title`, `detail` and `Content-Language` match the locale (SPRING-REST-13, NEST-REST-21).
  *Why:* codes are the contract.
- **TEST-I18N-06: A bundle parity test compares the key sets and `{n}` placeholders of all backend message bundles** (Spring: `messages_*.properties`; NestJS: ICU JSON catalogs, NEST-I18N-02).
  *Why:* missing backend texts otherwise show up only in production.
- **TEST-I18N-07: Locale-sensitive formatting has unit tests in at least two locales** (decimal and grouping separators, date order, currency position).
  *Why:* formatters silently use the wrong locale otherwise.
- **TEST-I18N-08: A language switch re-formats what is already on screen.** A component test renders a date and an amount, switches the active language without a reload, and asserts the new format and the new text.
  *Why:* a formatter that caches its result by input (a memoized function or a framework's cached formatter) keeps the old locale after a switch, and unit tests in two locales (TEST-I18N-07) do not see it.

| Layer | Addition |
|---|---|
| Unit (Vitest) | Formatters (pipes or functions: `money`, date, collator wrapper) in two locales (TEST-I18N-07); mapper test: an unknown code gives the generic key; store tests assert keys or codes only |
| Component | Real source catalog through the i18n library's testing helpers; role queries; axe; language-switch test (TEST-I18N-08) |
| E2E stubbed | Locale projects; assert `lang`/`dir`, axe, overflow check; pseudo-RTL nightly, non-blocking |
| E2E smoke | One critical path in a non-source locale against the real backend; the backend returns localized `detail` that the UI does not show (the UI shows its own text for the code) |
| Backend | REST adapter test per supported locale (Spring: `@WebMvcTest`); bundle parity; email rendering per locale; architecture test: no locale types (Spring: `Locale`, `MessageSource`; NestJS: NEST-I18N-05) in `domain`, `ports`, use cases |
| Manual (A11Y L6) | Screen reader pass in one non-source language: the voice switches correctly for foreign fragments |

## Open points

The tool behaviour this topic depends on (the stack's i18n library and testing helpers, re-formatting and component-library locale strings on a language switch, decimal-string input to `Intl.NumberFormat`, the Hibernate Validator locale, Weblate's `context.json` import, the pseudo-locale package, Weblate's licence) is confirmed in a spike before the first product adopts it: see [chapter 11](../../11-risks-and-technical-debt/README.md#verify-before-first-use).
