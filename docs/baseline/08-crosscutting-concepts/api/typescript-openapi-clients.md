# Generated API Clients (Orval)

How TypeScript projects consume REST APIs: clients, types, zod schemas and MSW mocks are generated with Orval from the pinned OpenAPI spec (API-CON-07/08). The generated code is an implementation detail of the outgoing HTTP adapter (TS-ARCH-05). The mapper turns wire formats from the [REST conventions](rest-conventions.md) into domain types: decimal strings into the domain's decimal representation (not a JavaScript `number` where precision matters), problem `code` values into the feature's domain errors (API-REST-01, API-REST-07).

Where the spec comes from depends on the repository layout ([07-deployment-view/repository-layout.md](../../07-deployment-view/repository-layout.md)):

| Layout | Orval input | Updated by |
|---|---|---|
| Same repository as the backend (shared default D12) | `../backend/openapi/<api>-v<N>.yaml` | the pull request that changes the backend spec |
| Separate repository | `./openapi/<api>-v<N>.yaml`, a pinned copy | a deliberate pull request with the spec diff (TS-API-08) |

## Layout

Paths relative to the frontend folder:

```
openapi/
  orders-v1.yaml                         ← only in a separate repository: pinned copy of the backend spec
orval.config.ts
src/features/orders/adapter/out/http/
  generated/                             ← Orval output, gitignored, regenerated by `npm run generate:api`
  http-orders.ts                         ← adapter implementing the ports
  orders-mapper.ts                       ← DTO ↔ domain mapping
  http-orders.spec.ts                    ← adapter test against MSW
```

One API used by several features: generate once into `src/platform/adapter/out/http/<api>/generated/` and let each feature's adapter import from there. The dependency-cruiser rule `generated-api-only-in-http-adapter` allows that path only from `adapter/out/http` folders.

## Configuration

```ts
// orval.config.ts (client and its override per stack, TS-API-03)
import { defineConfig } from 'orval';

export default defineConfig({
  orders: {
    input: { target: '../backend/openapi/orders-v1.yaml' }, // separate repo: './openapi/orders-v1.yaml'
    output: {
      mode: 'tags-split',
      target: './src/features/orders/adapter/out/http/generated/endpoints',
      schemas: './src/features/orders/adapter/out/http/generated/model',
      // client: …, override: { … }            // per stack: a client whose calls pass the platform HTTP stack
      mock: { generators: [{ type: 'msw', useExamples: true }] }, // key `mock` (singular) in Orval 8; the `orval` skill's `mocks` is wrong
      urlEncodeParameters: true, // TS-API-09: path parameters go through encodeURIComponent
      clean: true,
    },
  },
  ordersZod: {
    input: { target: '../backend/openapi/orders-v1.yaml' },
    output: {
      mode: 'tags-split',
      target: './src/features/orders/adapter/out/http/generated/endpoints',
      client: 'zod',
      fileExtension: '.zod.ts',
    },
  },
});
```

Option names change between Orval versions; the installed `orval` skill and orval.dev are the reference for the exact syntax. The generated MSW mocks import `@faker-js/faker`, so it is a dev dependency of every project that generates mocks (pinned like any other, TS-TOOL-13); the generated zod schemas need `zod` as a runtime dependency.

## Rules

- **TS-API-01: Orval generates clients, types, zod schemas and MSW mocks from the pinned spec**: the backend's committed spec in the same repository (`../backend/openapi/<api>-v<N>.yaml`), or the pinned copy in a separate repository (`openapi/<api>-v<N>.yaml`). `npm run generate:api` runs before `build`, `test` and `e2e`.
- **TS-API-02: Generated code is gitignored, never edited, and excluded from lint and coverage.** Customization goes into `orval.config.ts` (overrides, mutators), never into the output.
- **TS-API-03: The client mode is one whose calls pass the platform HTTP stack** (base URL, auth, XSRF, timeouts and error reporting configured once in `src/platform/adapter/out/http`); the stack names the Orval `client` and its override. **Query-library clients (the Orval `*-query` and `swr` clients) are not used.** They generate hooks that components call directly, which bypasses ports and use cases (TS-ARCH-04).
- **TS-API-04: Generated clients are not app-wide singletons.** The feature's composition file creates or provides them; only the adapter uses them.
- **TS-API-05: The adapter parses every response with the generated zod schema** before mapping (TS-ARCH-06). A parse failure becomes a technical error of the adapter, never a half-filled domain object.
- **TS-API-06: The adapter maps to domain types and returns `Promise`** (TS-D1), honoring the caller's `AbortSignal`: the signal reaches the HTTP call, so an aborted load cancels the request. A client that returns observables is converted with a shared helper that honors the signal (per stack).
- **TS-API-07: Batching and caching (API-N1 S4/S5) are decorators in the same folder**, implementing the same port and wrapping the plain adapter. They are wired in the composition file and have their own adapter tests (one batch call for N items, one call for repeated requests).
- **TS-API-08: A spec change is reviewed together with its effect on the frontend**: spec diff, regenerated code compiles, adapter tests green. In the same repository this is the pull request that changes the backend (REPO-API-01). With a separate repository, updating the pinned copy is its own pull request. A breaking change in the spec shows up as compile errors in the adapters, which is the point.
- **TS-API-09: `urlEncodeParameters: true` is set in every Orval client output.** Without it Orval interpolates path parameters raw into the URL template (`/orders/${orderId}`), so a value containing `/`, `?` or `#` changes the path or query of the request (another endpoint of the same API, injected query parameters; OWASP ASVS 5.0 V1 encoding). With it the generated code calls `encodeURIComponent(String(orderId))`. **Encoding does not stop dot segments:** `encodeURIComponent('..')` is `..`, and `new URL()` resolves `..` and `%2e%2e` segments, so `/orders/../admin` still leaves the intended path. Therefore id path parameters also get a format constraint in the spec (`pattern`, `format: uuid`), which the domain value object and the backend enforce, and code that sends the request (a server-side relay or mutator) asserts that the resolved URL stays on the expected origin and path prefix.
- **TS-API-10: Downloads of generated files (exports, reports) go through the outgoing HTTP adapter** by default: the generated client or `HttpClient`/`fetch` with a blob response, saved from an object URL. The adapter's error mapping, the 401 handling and error reporting then apply, and the UI can show progress (UI-20). The core never builds API URLs; the outgoing port returns the file (name, type, content). A plain `<a href download>` to an API path is acceptable only where a failed download needs no message, with the reason in the pull request. With a blob response type the error body arrives as a `Blob` too (Angular puts it in `HttpErrorResponse.error`, `fetch` in the response), so the adapter reads it (`await blob.text()`) and parses it as `application/problem+json` before the mapper of TS-ARCH-18 sees it; otherwise every business error of the download (too many rows, period too long) becomes a generic technical error. The adapter test answers the download with a problem body and asserts the domain error.
  *Why:* a browser download of an error response either saves the problem JSON as a file or fails silently, and a hand-built URL does not break the build when the API changes.

## Examples

### Request coalescing (API-N1 S4)

```ts
// coalescing-customers.ts: N single lookups in one tick → one batch request
// (no Promise.withResolvers: it is ES2024 and outside the supported browsers, TS-TOOL-02)
interface Deferred<T> { resolve: (value: T) => void; reject: (reason: unknown) => void }

export class CoalescingCustomers implements LoadCustomerPort {
  private queue = new Map<string, Deferred<Customer>[]>();
  private scheduled = false;

  constructor(private readonly http: HttpCustomers) {} // has loadCustomers(ids) → batch endpoint

  loadCustomer(id: CustomerId): Promise<Customer> {
    return new Promise<Customer>((resolve, reject) => {
      this.queue.set(id.value, [...(this.queue.get(id.value) ?? []), { resolve, reject }]);
      if (!this.scheduled) {
        this.scheduled = true;
        queueMicrotask(() => void this.flush());
      }
    });
  }

  private async flush(): Promise<void> {
    const batch = this.queue;
    this.queue = new Map();
    this.scheduled = false;
    try {
      const found = new Map((await this.http.loadCustomers([...batch.keys()])).map((c) => [c.id.value, c]));
      for (const [id, waiting] of batch) {
        const customer = found.get(id);
        for (const w of waiting) {
          if (customer) w.resolve(customer);
          else w.reject(new CustomerNotFound(id));
        }
      }
    } catch (error) {
      for (const waiting of batch.values()) for (const w of waiting) w.reject(error);
    }
  }
}
```

### Cache with in-flight dedupe (API-N1 S5)

```ts
export class CachedCountries implements LoadCountriesPort {
  private cached?: { at: number; value: Promise<readonly Country[]> };

  constructor(private readonly http: HttpCountries, private readonly ttlMs = 10 * 60_000) {}

  loadCountries(): Promise<readonly Country[]> {
    if (!this.cached || Date.now() - this.cached.at > this.ttlMs) {
      const value = this.http.loadCountries();
      value.catch(() => { this.cached = undefined; }); // don't cache failures
      this.cached = { at: Date.now(), value };
    }
    return this.cached.value;
  }
}
```

### Adapter test with generated MSW handlers

```ts
const server = setupServer();
beforeAll(() => server.listen({ onUnhandledFrame: 'error' })); // MSW 3; `onUnhandledRequest` in MSW 2
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

it('maps open orders to domain orders', async () => {
  server.use(getListOrdersMockHandler({ items: [openOrderDto({ id: 'o-1' })] }));
  const orders = await adapter.loadOrders(CustomerId.of('c-1'));
  expect(orders).toEqual([anOpenOrder('o-1')]);
});

it('rejects a malformed response', async () => {
  server.use(getListOrdersMockHandler({ items: [{ id: 42 }] } as never));
  await expect(adapter.loadOrders(CustomerId.of('c-1'))).rejects.toThrow();
});
```

## Skill overrides (`orval` skill)

Stack-specific rows are in the stack's clients doc.

| Skill says | Our rule |
|---|---|
| Query-library clients (TanStack Query, SWR) generated by Orval | Not used; a plain client behind ports (TS-API-03) |
| Generated client used directly in components | Only adapters use generated code (TS-ARCH-04/05) |
| Output key `mocks` for MSW generation | `mock` (singular), as in the configuration above; check the installed Orval's types when upgrading |
| camelCase zod schema names (`listOrdersResponse.parse`) | Orval 8.47's zod output is PascalCase operationId + `Response` (`ListOrdersResponse`); the naming has changed between Orval versions, so use the names from the generated `*.zod.ts` |
