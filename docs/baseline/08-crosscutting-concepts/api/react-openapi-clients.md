# React: Generated API Clients

The React mechanism for the generated-client rules in [typescript-openapi-clients.md](typescript-openapi-clients.md) (TS-API-*): Orval's `fetch` client with one platform mutator, generated zod schemas and MSW handlers, and HTTP adapters that parse, map and honor the caller's `AbortSignal`. Applies to the React SPA and to client-side calls in Next.js. Wiring: [05-building-block-view/react.md](../../05-building-block-view/react.md) (REACT-ARCH-12). Defaults: REACT-D8 in [04-solution-strategy/react.md](../../04-solution-strategy/react.md).

## Configuration

```ts
// orval.config.ts
import { defineConfig } from 'orval';

const input = { target: '../backend/openapi/orders-v1.yaml' }; // separate repository: './openapi/orders-v1.yaml' (TS-API-01)
const generated = './src/features/orders/adapter/out/http/generated';

export default defineConfig({
  orders: {
    input,
    output: {
      mode: 'tags-split',
      target: `${generated}/endpoints`,
      schemas: `${generated}/model`,
      client: 'fetch', // plain functions; every call passes the platform mutator (TS-API-03)
      override: {
        mutator: { path: './src/platform/adapter/out/http/custom-fetch.ts', name: 'customFetch' },
        fetch: { includeHttpResponseReturnType: false }, // the mutator returns the body; the adapter zod-parses it
      },
      mock: { generators: [{ type: 'msw', useExamples: true }] },
      urlEncodeParameters: true, // path parameters are encodeURIComponent-ed
      clean: true,
    },
  },
  ordersZod: {
    input,
    output: { mode: 'tags-split', target: `${generated}/endpoints`, client: 'zod', fileExtension: '.zod.ts' },
  },
});
```

Per operation Orval 8.47 generates a function (`listOrders(params, options)`, `cancelOrder(orderId, body, options)`) that calls `customFetch<T>(url, init)`, a zod schema per response in `*.zod.ts` with **PascalCase** names (`ListOrdersResponse`, `CancelOrderResponse`), and in `*.msw.ts` a handler per operation (`getListOrdersMockHandler`), a response factory (`getListOrdersResponseMock`) and `getOrdersMock()` with all handlers. The generated code imports the mutator by a relative path with its `.ts` extension, which compiles because the tsconfig sets `allowImportingTsExtensions` (REACT-ARCH-17).

## Rules

### Client generation

- **REACT-API-01: Orval uses `client: 'fetch'` with the platform mutator `customFetch`** (TS-API-03, REACT-D8). The `react-query`, `swr` and other query-library clients are not generated: they produce hooks that components call directly, past ports and use cases. Data loading with TanStack Query happens in the UI adapter and calls use cases (REACT-ARCH-13).
- **REACT-API-02: `override.fetch.includeHttpResponseReturnType: false`.** The generated function returns the body as the mutator returned it, not `{ data, status, headers }`. Status handling is done once, in the mutator (REACT-API-05); the adapter only sees a body or an error.
- **REACT-API-03: `urlEncodeParameters: true` is mandatory.** Without it Orval 8.47 interpolates path parameters raw into the URL, so a value with `/`, `?` or `#` changes the request target. With it the URL is built with `encodeURIComponent(String(orderId))`. Encoding does not neutralize a `..` value (dot segments survive `encodeURIComponent` and are resolved by `new URL()`): id parameters also need a `pattern` or `format` in the spec (TS-API-09), and the mutator rejects a resolved URL outside the own origin (REACT-API-05).
- **REACT-API-04: MSW handlers and zod schemas are generated too**: `mock: { generators: [{ type: 'msw', useExamples: true }] }` (key `mock`, singular) and a second output with `client: 'zod'`. The MSW output imports `@faker-js/faker`, which is therefore a dev dependency. Generated code is gitignored, excluded from ESLint and Prettier, and regenerated by `npm run generate:api` before `test` and `build` (TS-API-01/02).

### The mutator

- **REACT-API-05: `customFetch` in `src/platform/adapter/out/http/custom-fetch.ts` is the only place that turns an HTTP exchange into a result or an error:**

  | Situation | Behaviour |
  |---|---|
  | Every call | URL resolved against `location.origin` (relative, same-origin paths only, no build-time base URL, CFG-11); `credentials: 'same-origin'`; `Accept: application/json, application/problem+json` |
  | Resolved URL on another origin | `TechnicalError('unexpected')`, reported once, nothing sent (a contract error) |
  | Mutating method (`POST`, `PUT`, `PATCH`, `DELETE`) to the same origin | `X-XSRF-TOKEN` header from the BFF's `XSRF-TOKEN` cookie; never to another origin, never on `GET` ([security/react.md](../security/react.md)) |
  | Timeout | the caller's signal combined with `AbortSignal.timeout(timeoutMs)` by the platform helper `anySignal` (below); `timeoutMs` from `/config.json` (RES-TMO-01) |
  | 2xx | body as `unknown` cast to the generated type; `204` returns `undefined`; a body that is not JSON becomes `TechnicalError('malformed-response')`, reported once with the status |
  | 401 | calls `onUnauthorized` (navigates to the BFF login path from `/config.json`), throws `TechnicalError('unauthorized')`, not reported |
  | 5xx | `TechnicalError('server')`, reported once with `status` and the problem's `traceId` (OBS-14) |
  | Network failure, time-out | `TechnicalError('network' / 'timeout')`, reported once |
  | Caller aborted | the abort error is rethrown unchanged and not reported |
  | Other 4xx | `HttpProblem(status, problem)` for the feature's mapper (TS-ARCH-18) |

  The mutator never retries (RES-RTY-04: retries live in one layer, the query client's transient-only policy, REACT-ARCH-13) and never adds an `Authorization` header: the browser holds no tokens (TS-SEC-01). It does not use `AbortSignal.any`: that needs Firefox 124 and Safari 17.4, beyond the TS-TOOL-02 browser set (Firefox 119, Safari 17.0), and the compiler's `DOM` lib does not catch it. The small `anySignal` helper next to the mutator combines the signals instead; it passes the mutator's time-out and abort tests in Vitest, and running it in Firefox 119 and Safari 17.0 is to be verified before first use.
- **REACT-API-06: The mutator is configured once with `configureHttp()`** from `createPlatform()` before the first render (REACT-ARCH-12; (React SPA) its settings come from `/config.json`, Next.js: NEXT-API-05). Orval's `fetch` client generates module functions, not injectable instances, so the mutator reads module-level settings (`timeoutMs`, `onUnauthorized`, `reportError`); a call before `configureHttp()` throws. This is how TS-API-04 applies in React: the generated functions are stateless; the adapter that uses them is an instance created by the feature's factory (REACT-ARCH-10), and dependency-cruiser keeps everything else away from them (`generated-api-only-in-http-adapter`).
- **REACT-API-07: Only generated code imports the mutator.** dependency-cruiser `http-mutator-only-from-generated`, with the mutator exempted from `platform-only-via-index` because generated code reaches it by a deep relative path (REACT-ARCH-22). Features never call `customFetch` themselves; a hand-written request in a feature is a missing operation in the spec (API-CON-07).
- **REACT-API-08: The mutator reads problem bodies with a small platform schema of the convention fields the frontend relies on** (`code`, `traceId`, `errors[]`, API-REST-07). It serves every API and cannot import one feature's generated model. It is not a DTO: features map from `HttpProblem`, never from their own copy of a problem type.
- **REACT-API-09: Plain `fetch` outside generated clients exists only in platform adapters that run before or beside the HTTP stack**: the runtime-config loader (`/config.json`, before `configureHttp()`) and the error-reporting sender (which must not report its own failures). Each sets its own timeout with `AbortSignal.timeout(…)` (RES-TMO-01); the reporting sender adds the XSRF header and drops a failed send silently. ESLint `no-restricted-globals` allows `fetch` only under `adapter/out/http` (REACT-ARCH-12).

```ts
// src/platform/adapter/out/http/custom-fetch.ts (excerpt)
/** AbortSignal.any needs Firefox 124 / Safari 17.4, beyond the TS-TOOL-02 browser set. */
export function anySignal(...signals: readonly AbortSignal[]): AbortSignal {
  const controller = new AbortController();
  for (const signal of signals) {
    if (signal.aborted) {
      controller.abort(signal.reason);
      break;
    }
    signal.addEventListener('abort', () => { controller.abort(signal.reason); }, { once: true, signal: controller.signal });
  }
  return controller.signal;
}

export async function customFetch<T>(url: string, init: RequestInit): Promise<T> {
  if (settings === undefined) throw new Error('customFetch called before configureHttp');
  const { timeoutMs, onUnauthorized, reportError } = settings;
  const target = new URL(url, globalThis.location.origin);
  if (target.origin !== globalThis.location.origin) {
    const failure = new TechnicalError('unexpected'); // same-origin paths only (REACT-API-05)
    reportError.report(failure);
    throw failure;
  }
  const timeout = AbortSignal.timeout(timeoutMs);
  const signal = init.signal ? anySignal(init.signal, timeout) : timeout;
  const headers = withXsrfHeader(new Headers(init.headers), init.method ?? 'GET', target);
  headers.set('Accept', 'application/json, application/problem+json');

  let response: Response;
  try {
    response = await fetch(target, { ...init, headers, signal, credentials: 'same-origin' });
  } catch (error) {
    if (init.signal?.aborted === true) throw error; // cancelled by the caller: not a failure
    const failure = new TechnicalError(timeout.aborted ? 'timeout' : 'network', { cause: error });
    reportError.report(failure);
    throw failure;
  }

  if (response.ok) {
    try {
      return (await readBody(response)) as T; // the adapter parses it with the generated zod schema
    } catch (error) {
      const failure = new TechnicalError('malformed-response', { cause: error }); // not JSON
      reportError.report(failure, { status: response.status });
      throw failure;
    }
  }
  if (response.status === 401) {
    onUnauthorized();
    throw new TechnicalError('unauthorized');
  }
  const problem = await readProblem(response);
  if (response.status >= 500) {
    const failure = new TechnicalError('server');
    reportError.report(failure, { status: response.status, ...(problem.traceId && { traceId: problem.traceId }) });
    throw failure;
  }
  throw new HttpProblem(response.status, problem);
}
```

### The adapter

- **REACT-API-10: The feature's HTTP adapter passes the caller's signal, parses with the generated zod schema, maps in one mapper and reports the technical errors it creates.** It calls the generated function with `{ signal: signal ?? null }` (`RequestInit.signal` is `AbortSignal | null`, and `exactOptionalPropertyTypes` rejects `undefined`), so an aborted query cancels the request (TS-API-06). It reads the body as `unknown` and parses it with `safeParse`; a mismatch becomes `TechnicalError('malformed-response')`, never a half-filled domain object (TS-API-05). The mapper turns DTOs into domain types and `HttpProblem`s into the feature's domain errors (TS-ARCH-18): known problem `code` → business error, 404 → not found, 400 → validation error with the field codes, anything else → `TechnicalError('unexpected')`; `TechnicalError` and abort errors pass unchanged. The adapter receives the platform's `ReportErrorUseCase` in its constructor from the feature's factory (REACT-ARCH-10) and reports the two `TechnicalError`s it creates, once; one it passes on was reported by the mutator (REACT-OBS-04). Parsing runs outside the `try` around the call, so the mapper never sees a parse failure.

```ts
// features/orders/adapter/out/http/http-orders.ts
export class HttpOrders implements LoadOrdersPort, CancelOrderPort {
  constructor(private readonly reportError: ReportErrorUseCase) {}

  async loadOrders(query: LoadOrdersQuery, signal?: AbortSignal): Promise<OrderPage> {
    let body: unknown;
    try {
      body = await listOrders({ page: query.page, size: query.size }, { signal: signal ?? null });
    } catch (error) {
      // no business errors here: any HttpProblem → TechnicalError('unexpected')
      throw this.reportedIfCreated(toLoadOrdersError(error), error);
    }
    return toOrderPage(this.parse(ListOrdersResponse, body));
  }

  async cancelOrder(command: CancelOrderCommand, signal?: AbortSignal): Promise<Order> {
    let body: unknown;
    try {
      body = await cancelOrder(command.orderId, { reason: command.reason }, { signal: signal ?? null });
    } catch (error) {
      throw this.reportedIfCreated(toOrdersError(error, command.orderId), error);
    }
    return toOrder(this.parse(CancelOrderResponse, body));
  }

  private parse<T extends z.ZodType>(schema: T, body: unknown): z.output<T> {
    const result = schema.safeParse(body);
    if (result.success) return result.data;
    const failure = new TechnicalError('malformed-response', { cause: result.error });
    this.reportError.report(failure);
    throw failure;
  }

  /** Reports a TechnicalError the mapper created; one passed on unchanged was reported where it was created. */
  private reportedIfCreated(mapped: unknown, original: unknown): unknown {
    if (mapped !== original && mapped instanceof TechnicalError) this.reportError.report(mapped);
    return mapped;
  }
}

// features/orders/adapter/out/http/orders-mapper.ts (problem mapping)
export function toLoadOrdersError(error: unknown): unknown {
  return error instanceof HttpProblem ? new TechnicalError('unexpected', { cause: error }) : error;
}

export function toOrdersError(error: unknown, orderId: string): unknown {
  if (!(error instanceof HttpProblem)) return error; // TechnicalError or the caller's abort: unchanged
  if (error.problem.code === 'ORDER_ALREADY_SHIPPED') return new OrderAlreadyShipped(orderId);
  if (error.status === 404) return new OrderNotFound(orderId);
  if (error.status === 400) return new CancelOrderRejected(error.problem.errors ?? []);
  return new TechnicalError('unexpected', { cause: error });
}
```

- **REACT-API-11: Batching and caching decorators (API-N1 S4/S5) implement the same port and wrap the adapter in the feature's factory in `<feature>.api.tsx`** (TS-API-07, REACT-ARCH-10): `const loadCustomers = new CoalescingCustomers(new HttpCustomers(reportError))`; a cache that must outlive one visit of the screen is held in a module-level value of that file. They are not TanStack Query features: the query cache is a UI cache of use-case results, the decorator reduces backend calls for every caller.

### Tests

- **REACT-API-12: Adapters and the mutator are tested against MSW with the generated handlers** (TS-TEST-04). `setupServer()` from `msw/node`, `server.listen({ onUnhandledFrame: 'error' })` (MSW 3 renamed `onUnhandledRequest`), `resetHandlers()` after each test, and `configureHttp()` with a mocked report-error use case before each test. Generated handlers take a response or a resolver (`getListOrdersMockHandler(({ request }) => …)`), factories take overrides (`getCancelOrderResponseMock({ id: 'o-1' })`); problem responses are written with `http.*` and `HttpResponse.json(…, { status, headers: { 'Content-Type': 'application/problem+json' } })`. The adapter is constructed with the same `mock<ReportErrorUseCase>()`. Each adapter covers: mapping of a success, the request it sends (query parameters, body), a malformed response (reported once by the adapter), a 5xx reported exactly once (by the mutator) with its `traceId`, each known problem `code` and 404 (not reported), an unknown code (reported once) and a caller abort (not reported). The mutator's own test covers: XSRF header only on same-origin mutating calls, a malformed XSRF cookie treated as absent, a target on another origin rejected and reported, 401 (callback, no report), 4xx passed on as `HttpProblem`, a non-JSON 2xx body reported, time-out reported (`delay('infinite')`, RES-TMO-03), network failure reported (`HttpResponse.error()`), caller abort not reported.

```ts
const server = setupServer();
const problem = (status: number, code?: string) =>
  HttpResponse.json(
    { type: 'about:blank', title: 'Problem', status, ...(code && { code }), traceId: 'trace-1' },
    { status, headers: { 'Content-Type': 'application/problem+json' } },
  );

beforeAll(() => { server.listen({ onUnhandledFrame: 'error' }); });
beforeEach(() => { configureHttp({ timeoutMs: 1_000, onUnauthorized: () => undefined, reportError }); });
afterEach(() => { server.resetHandlers(); reportError.report.mockReset(); });
afterAll(() => { server.close(); });

it('maps ORDER_ALREADY_SHIPPED to the business error', async () => {
  server.use(http.post('*/api/v1/orders/:orderId/cancel', () => problem(409, 'ORDER_ALREADY_SHIPPED')));
  await expect(adapter.cancelOrder(command)).rejects.toEqual(new OrderAlreadyShipped('o-1'));
  expect(reportError.report).not.toHaveBeenCalled();
});

it('rejects a malformed response with a technical error and reports it, because the adapter created it', async () => {
  server.use(getListOrdersMockHandler({ items: [{ id: 42 }] } as never));
  const failure: unknown = await adapter.loadOrders({ page: 0, size: 20 }).catch((error: unknown) => error);
  expect(failure).toMatchObject({ failure: 'malformed-response' });
  expect(reportError.report).toHaveBeenCalledExactlyOnceWith(failure);
});
```

- **REACT-API-13: With several features, every OpenAPI tag is generated into exactly one owning feature.** The template configures one feature; a second feature does not copy the config with an overlapping tag list. `orval.config.ts` lists, per feature, the tags it owns (`input.filters: { tags: [...] }` for both the `fetch` and the `zod` output), and the tag sets are disjoint. A feature that needs an operation another feature owns uses that feature's use case through its published API (TS-ARCH-19, REACT-ARCH-11); the backend splits a tag that two features really share. A check in `check:arch` or the config's own test fails when two features generate the same tag.
  *Why:* overlapping tag lists triple the generated code, double every diff after an API change, and leave near-identical adapters that must be kept in sync by hand.

## Skill overrides (`orval`, `tanstack-query-best-practices`)

| Skill says | Our rule |
|---|---|
| `client: 'react-query'` / `swr`, or the `tanstack-query.md` guide | Plain `fetch` client behind ports; TanStack Query calls use cases (REACT-API-01) |
| Fetch mutator returns `{ status, data, headers }` | `includeHttpResponseReturnType: false`; status handled in the mutator (REACT-API-02, REACT-API-05) |
| `Authorization: 'Bearer …'` header in the mutator | No tokens in the browser; BFF cookie plus XSRF header (REACT-API-05, TS-SEC-01) |
| `baseUrl` per environment, or from the spec's servers | Relative same-origin paths; per-environment values only from `/config.json` (REACT-API-05, CFG-11) |
| `override.fetch.runtimeValidation: true` | The adapter parses with the generated zod schema and chooses the error (REACT-API-10, TS-API-05) |
| `mocks: true` (MSW plus faker files) | `mock: { generators: [{ type: 'msw', useExamples: true }] }` (REACT-API-04) |
| `urlEncodeParameters` as an option | Mandatory (REACT-API-03) |
| zod names in camelCase (`listOrdersResponse`) | Orval 8.47 emits PascalCase (`ListOrdersResponse`); use the names in the generated `*.zod.ts` |
| `server.listen({ onUnhandledRequest: 'error' })` | MSW 3: `onUnhandledFrame: 'error'` (REACT-API-12) |
| `queryFn` calls generated API functions | `queryFn` calls a use case (REACT-ARCH-13) |
